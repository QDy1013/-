# 自动读取稳定性

自动读取是整个 App 的基础。能在软件层面做的加固分四件事。系统层面的限制（厂商后台管控、免打扰群不发通知）代码解决不了，只能靠诊断和引导。

## 1. 通知处理不能崩
`NotifListener.onNotificationPosted` 整体包在 try/catch（Throwable）里。任何异常只写进诊断日志，不向外抛。服务一旦崩溃，系统会把它解绑，之后收不到任何消息。

## 2. 看门狗
一个周期 15 分钟的后台任务（JobScheduler，开机后保持）：通知读取权限已开、但服务没连上时，请求系统重新绑定；仍然没连上，就把服务组件先停用再启用，强制系统重新绑定。App 启动、开机、应用更新后都会重新登记这个任务。

## 3. 诊断日志 `com.nopalou.DiagLog`（纯 Java，不依赖 Android）
环形缓冲，容量 50 条，最新的在后。静态方法：
- `reset()`：清空日志和计数（测试用）。
- `record(long now, String kind, String detail)`：记一条。`kind` 只会是这几个：`收到`（通知进来并交给引擎）、`跳过`（通知被忽略，detail 写原因，如"汇总通知""没有正文""来源不在白名单"）、`出错`（异常，detail 写异常类名和信息）、`重连`（看门狗或界面请求了重新绑定）、`连接`（服务连上）、`断开`（服务断开）。
- `List<DiagLog.Entry> recent(int n)`：最近 n 条，**最新的在前**；n 大于现有条数就全返回；n<=0 返回空列表。Entry 有公开字段 `long time`、`String kind`、`String detail`。
- `int count(String kind)`：某一类累计条数（不受 50 条容量限制，只要没 reset 就一直累加）。
- `String dump()` 和 `static void load(String s)`：把日志和计数序列化成一个字符串，以及从字符串恢复（用于落盘）。`load` 会先 reset 再恢复；传入 null、空串或格式损坏的内容时不抛异常，结果是空日志。`dump` 后 `load` 再 `recent`、`count` 必须和原来一致。
- detail 里可能含换行、制表符，dump/load 必须能无损往返。

## 4. 自检 `com.nopalou.HealthCheck`（纯 Java）
`static HealthCheck.Result evaluate(boolean accessEnabled, boolean connected, boolean batteryIgnored, long lastReceivedAt, long now)`。

Result 有：`int level`（0 正常，1 提醒，2 严重）、`List<HealthCheck.Issue> issues`、`String summary()`。Issue 有 `int level`、`String text`、`String fix`。

规则，按这个顺序追加问题：
1. `accessEnabled` 为假 → 严重（2）：text `通知读取权限没开，App 收不到群消息`，fix `NOTIF_ACCESS`。
2. `accessEnabled` 为真且 `connected` 为假 → 严重（2）：text `权限已开，但系统还没有连上通知服务（正在自动重连）`，fix `REBIND`。
3. `batteryIgnored` 为假 → 提醒（1）：text `电池没有设成不限制，系统可能在后台把它关掉`，fix `BATTERY`。
4. `connected` 为真且 `lastReceivedAt > 0` 且 `now - lastReceivedAt > 72 小时` → 提醒（1）：text `已经超过 3 天没收到群消息，请确认群没有开免打扰`，fix `MUTE`。
- `level` 取所有问题里最大的，没有问题是 0。
- `summary()`：没有问题返回 `自动读取正常`；否则返回 `发现 N 个问题`（N 是问题数）。
